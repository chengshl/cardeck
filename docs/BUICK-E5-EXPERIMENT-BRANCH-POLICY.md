# Buick-E5 变更风险分级与短期试验分支规则

> 状态：2026-10-26 用户确认；此文档是**后续开发流程约束**，不代表当前任务已通过手机或实车验收。原始决策：[#17](https://github.com/chengshl/cardeck/issues/17#issuecomment-6408712963)；总清单：[#12](https://github.com/chengshl/cardeck/issues/12#issuecomment-6408716751)。

## 分支职责

- `Buick-E5`：当前稳定基准，可持续优化易用性和 UI，但保护已验证的连接、触摸、视频、更新能力。
- `Buick-Test`：过渡集成测试分支，择优吸收上游与 E5 已验证功能；未来可取消。
- `Buick`：最终正式发行分支，只从经过集成验证的功能中选择性合并。
- `experiment/*`：按任务创建的短期试验分支；失败允许保留证据，不得自动污染 E5 / Buick。

## 变更类型与处理门槛

| 等级 | 举例 | 开发与验收路径 |
|---|---|---|
| L1 低风险 | 文案、色彩、图标、间距、纯静态排版（没有状态、数据和行为改变） | 允许直接 E5；至少代码检查、CI 检查与必要的手机 UI 确认。 |
| L2 中风险 | 更新弹窗与页面逻辑、版本来源识别、APK 下载/安装/回退、设置持久化、权限、后台任务与生命周期 | **先建 `experiment/buick-e5-<task>`**；编译/单测及针对性手机实测后，才能选择性合并 E5，再次验证后发布。 |
| L3 高风险 | CarPlay/iAP2/AirPlay、BT/Wi-Fi 音视频通道、Shizuku、虚拟屏、异常重连、系统崩溃/重启 | **必须独立试验**，单变量/可回退方案、详细日志、CI + 多轮实车回归与专项验收指标；未经证明不得合并稳定线。 |

判定以**可能损坏的能力**为准，不以改动行数或是否位于 UI 文件为准。若同一任务同时涉及多级，按最高风险执行。

## 执行步骤

1. 变更前记录需求、风险等级、基准 SHA、预期/禁止改变的行为、验收条件和回滚策略；L2/L3 先建短期试验分支。
2. 专项 Issue 留痕：分支名、提交、差异、构建与版本、手机或实车测试条件、截图/脱敏日志、成功/失败/未测、结论；**失败试验不覆盖历史**。
3. CI 成功仅证明自动化检查通过，不代表 APK 安装、更新器、手机 UI 或车机实测通过。针对更新系统，至少核验当前安装包来源、更新检查通道、正式/实验版页面、版本/构建时间、SHA256、Android 版本升级限制与安装权限。
4. 实际验收通过后仅将所需提交或文件移植至 E5；避免直接把整个 experiment 分支覆盖过去。移植后再次 CI、手机/实车回归，达标才形成新的稳定基准。
5. 任务完成后记录最终结论；临时试验分支经确认可删除，提交、Issue 与历史 Release 保留；`backup/`、`milestone/` 禁止擅自删除。

## APK 安装隔离的特别说明

Git 分支隔离**不等于**手机安装隔离。若试验 APK 与 `Buick-E5` 使用相同 `applicationId`，安装就可能覆盖原 E5，且 `versionCode` 不允许普通覆盖降级。必要时使用备用测试手机，或另行评估可并存的独立包名、签名、授权与更新通道；未经实现验证，不能承诺“试验安装后可无损回退”。

## 2026-10-26 软件更新 UI 流程复盘

E5 本轮 UI 更新涉及正式版弹窗、试验包文件保存、安装过程、构建来源等逻辑，属于 **L2 中风险**，按新规则应先走独立实验分支。此前已直接提交 E5 并经 CI 构建发布，但仍需手机实装验收；**不得把 CI 成功记作 UI 或实车验收成功**。此条作为以后采用新流程的依据，不倒推宣称已建立试验分支或通过真实测试。

## 维护方式

每次更改风险规则需在 #17 留决策记录、#12 留简明索引。仅文档更新不应触发无意义的稳定 APK 发版；代码、APK 发布与手机/实车验收分别记录。
