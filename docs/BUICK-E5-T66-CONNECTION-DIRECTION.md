# Buick E5/B233 · T65→T66 连接方向与 0x4300 ACK 对照

> 日期：2026-10-24（北京时间），仅来源于 CarDeck Gateway 中已上传的实车日志；状态：**待进一步实车验证**。

## 确认的事实（不是推测）

| 场景 | 时间（北京时间） | 蓝牙 RFCOMM 建链方向 | 0x4300 / 0x4301 |
|---|---|---|---|
| 旧版成功样本 | 2026-10-23 11:51:49–11:51:55 | 手机连车机配件端 | 75B `0x4300` 获 peer ACK；约 125ms 内收到 `0x4301` |
| T65 首轮失败 | 2026-10-24 15:54:32–15:54:57 | 车机主动连入手机 iAP2 | `0x4300` 为 seq110，peer ACK 停在 109；车机重复 DETECT/SYN；约 20s 超时 |
| T65 同轮备用连接失败 | 2026-10-24 15:54:59–15:55:23 | 手机连车机配件端 | 同样 `0x4300` seq110 未获 ACK、约 20s 超时 |

三个样本的 B233 设备识别、32B MFi 挑战及 75B 双组 `0x4300` 都进入预期步骤；`0xAA05` 是发送端自报“认证成功”，不能当成车机最终接受 CarPlay 的证据。

**因同轮手机主动连接也失败，不能仅凭这三次就判定是 RFCOMM 连接方向本身导致拒绝。** 更可能还涉及车机 CarPlay 会话占用、前一轮失败后的恢复状态、车机 UI 连接意图或配对状态；以上均未被日志证明。

## T65 的可复现重连缺陷

- 15:54:32 收到 B233 ACL_CONNECTED，许可最多两次手机侧兼容拨号。
- 15:54:32 车机主动 iAP2 连接被接受；旧许可清除。
- **15:54:38 HFP CONNECTED** 被旧 T65 策略错误识别成新邀请，重新授权手机拨号。
- 首轮 iAP2 失败后，15:54:58 即再次进行手机主动拨号，违反“车机连接请求才触发一轮”的设计。

## T66 修改

- 不再把 HFP/A2DP CONNECTED 当成车机 CarPlay 请求，**只识别新的 ACL_CONNECTED 物理建链事件**。
- 一次 ACL 会话仅能授权一轮；必须观察到 ACL_DISCONNECTED 再 ACL_CONNECTED 才能重新授权；手机主动停止/重启也会清理状态。
- 许可仅适用于产生事件的同一车机，地址仅进程内暂存，不在日志/设置中保存。
- 车机反向 iAP2 优先；ACL 到来后等待 1500ms，再允许同车机最多两次有限的配件端 RFCOMM 兼容拨号；手机设置里的单次手动诊断不变。
- 提前进行 B233 许可检查，避免等待车机时每三秒重复记录强制握手/配置文件。
- 明确记录 B233 建链方向与 `0x4300` 无 ACK 的情况；**未改动 75B `0x4300` 的字段/尺寸、MFi 32B 或 AirPlay 音视频逻辑**。
- 仅提交到 Buick-Test；Buick-main/Buick-E5 不受影响。

## 下一轮实车验证

1. 手机开启 T66 服务，车机端选择该手机。观察是否进入 `BT T66: 建链方向=车机主动连接手机`。
2. 如果 `0x4300` 未获 ACK，确认**不会**因随后 HFP/A2DP CONNECTED 自动发起第二轮拨号。
3. 车机明确断开再重新连接（确保 ACL 完整断开后重新建立），验证车机确实重新发起新一轮。
4. 无法连接时从 Test 别克设置点击**单次手动 iAP2 兼容连接**，比较已知成功的手机→车机方向。
5. 采集并比对“失败后保持车机状态”和“车机重启/新连接窗口”的 0x4300 ACK 与 DETECT/SYN 时间线；当前证据不足以改变报文字节。

如遇实际手机系统重启，另按 system_server/Shizuku 虚拟屏链路处理，不能混为同一故障。
