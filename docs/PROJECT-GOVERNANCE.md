# CarDeck 项目统一开发与协作规则

> **统一规范版本：2026-10-26 / v1.4**  
> **唯一权威来源**：`Buick:docs/PROJECT-GOVERNANCE.md`。本文件在 `Buick-E5`、`Buick-Test` 是完全一致的只读同步副本，不允许各分支单独改写规则。与历史 `AGENTS.md`、旧版分支文档、Issue 快照冲突时，按本规则及用户最新明确决定执行。

## 一、仓库与分支边界

| 分支 | 职责 | 规则同步 |
|---|---|---|
| `Buick` | 最终正式发行版，择优吸收集成验证通过的功能；本规则权威分支 | 唯一编辑入口 |
| `Buick-E5` | 当前稳定基准，保障连接、触摸、视频及在线更新可用，持续改善 UI/易用性 | 与 Buick 规则完全同步 |
| `Buick-Test` | 临时集成测试线，选择性吸收上游新功能与 E5 已验证功能；未来可能取消 | 与 Buick 规则完全同步 |
| `main` | 上游代码同步线，**不属于本项目规则同步范围** | 不修改 |
| `Buick-main` | 已由 Buick 取代的历史旧分支，保留兼容与追溯 | 不再同步 |
| `experiment/*`、`backup/*`、`milestone/*` | 任务试验、备份与里程碑快照 | 不批量同步；试验时以 Buick 最新规则为准；备份/里程碑不擅自改动 |

## 二、规则更新：一个权威版本、立即同步

1. 用户确认**开发规范、分支职责、命名、发布原则、记录格式、验收门槛、流程约定**等非运行功能决定后，在当次工作中立即更新 `Buick:docs/PROJECT-GOVERNANCE.md`，并同步同一字节内容到 `Buick-E5` 与 `Buick-Test`；同时按需在 GitHub Issue 留决策依据。不要只写聊天记录或当前工作分支。
2. `Buick` 的 `.github/workflows/sync-project-governance.yml` 对本文件的推送提供自动镜像，以尽量避免各分支规则漂移。同步失败时记录原因并及时补齐，**不能宣称未成功的同步已完成**。
3. 子分支 `AGENTS.md` 只保留与本分支代码有关的技术说明和指向本文件的入口；不能另建与统一规则冲突的独立治理制度。历史文档保留供追溯，但不改变本规范优先级。
4. **纯规则/文档提交不是软件更新**：不能因为修订 `docs/**`、`AGENTS.md` 等文档就自动构建或发布正式 APK。构建工作流配置路径过滤；文档同步禁止更改运行源码、包名、签名和版本号。
5. 当一次提交同时含运行功能变更和文档时，仍按功能变更完整执行对应 CI / APK 发布与验收流程；不得用 `[skip ci]` 绕过功能变更检查。手动触发正式构建须有明确需求。

### 每次任务启动前必须复核规范（v1.3，2026-10-26 用户明确要求）

**强制起点，不依赖聊天记忆：** 每当在新聊天中处理 CarDeck，或在已有聊天中开始一项新的、继续一项中断的开发/诊断/发布/记录任务时，**在提出实施方案、修改任何仓库内容、运行构建或给出基于旧进度的处理决定之前**，先实时读取 `Buick:docs/PROJECT-GOVERNANCE.md` 当前版本全文，并依次核实：

1. **规则与同步状态**：记录权威规范版本/提交或文件哈希，核对 `Buick-E5` 与 `Buick-Test` 的规则内容是否一致，以及最近镜像工作流是否成功；不得沿用上轮聊天记住的版本或把同步任务已启动当成同步成功。
2. **任务与代码现状**：从 #12 当前有效入口定位所属专项 Issue，阅读相关的最新结论与逐轮历史评论；核对目标分支当前 HEAD、最近提交、CI/Release、测试及回滚限制。#12 的历史快照、旧 `Buick-main`、过期版本号与旧渠道规则**不得高于本规范和用户最新明确决定**。
3. **先确认风险与操作边界**：按 L1/L2/L3 及当前功能线选对稳定/试验分支，明确本轮允许修改、必须隔离、待实车验证的范围；需要构建或交付时准备对应验收清单。新聊天继续旧实验应核对最新基线，不能盲目重开同功能分支。
4. **启动结论留痕**：处理实质任务时，在回复中简要说明使用的规范版本、目标分支、风险等级及发现的冲突；属于开发/实验的项目继续在专项 Issue 追加真实状态。预检不要求在每一次工具调用前重复，也不能变成阻碍简单问答的冗长仪式。
5. **规则变化与失联**：任务进行期间发现规范或用户决定已更新，应以最新权威文本重新确认影响后再合并/发布；若暂时无法读取权威规范或验证同步，明确告知“未核实”，**不得宣称符合规范，也不得贸然执行高风险变更、合并或发布**，待可核验后继续。

此项是**工作开始前的检查义务**，不能只靠 #12 提醒或助手的历史聊天记忆替代；仅更新文档及镜像流程，**不改变 APK 功能、签名、版本、构建或正式发布渠道**。

## 三、通用开发风险分级（适用于 CarDeck 所有活跃目标分支）

**风险分级是整个 CarDeck 项目的通用规则，不专属于 `Buick-E5`，也不决定默认修改哪条分支。** 每次先根据任务功能、分支职责和最新基线确定实际目标分支，再依风险等级决定实施、测试和合并门槛。

| 风险 | 典型改动 | 最小验证流程 |
|---|---|---|
| L1 低风险 | 纯静态文字、颜色、图标、间距，不改行为 | 可在**本次对应目标分支**直接修改；进行代码审查、必要的 CI 与适用的视觉/功能验证 |
| L2 中风险 | 更新页面与弹窗逻辑、APK 下载/安装、版本来源、权限、设置存储、生命周期 | 从**本次对应目标分支**建立独立短期 `experiment/<target>-<task>`；通过相关手机/功能验证后，选择性合入该目标分支 |
| L3 高风险 | CarPlay/iAP2/蓝牙/Wi-Fi、音视频流、Shizuku/虚拟屏、系统崩溃/重启 | 从兼容基线建立独立试验；预备可执行回退方案，明确设备/实车验收指标并做多轮实际测试；通过后才考虑选择性合入对应目标分支 |

**`<target>` 是目标分支/功能线的规范化标识，不固定为 `buick-e5`。** 例如针对 `Buick-Test` 的实验应从最新 Test 兼容基线派生，而不能仅因风险分级示例就强行转向 E5；针对其他分支同理。分支的正式发行/稳定/集成职责仍以本文件第一节为准。

按**潜在破坏的能力**分类，不按代码量大小判断；多个等级混合时从高。未验证的高风险代码不得直接进入任何承担稳定/正式使用职责的分支。

## 四、验证、交付与记录

- 每轮在相关专项 Issue 记录目标、风险级别、基准/试验分支、提交 SHA、CI、APK 版本与更新来源、测试条件、脱敏日志或截图、成功/失败/未测、结论、下一步、回滚策略。#12 为总清单索引；#17 为更新架构/试验版本相关专项。
- 明确区分：**仅方案 → 已提交 → CI通过 → APK已发布 → 手机端/实车验收通过 → 完成**。CI 通过不代表手机 UI 或车机稳定性通过。
- 试验验证通过后只合并所需提交/文件，不用整分支覆盖；**每条实际接收改动的目标分支**均须重新核验、构建与按职责独立发布/验收。高风险问题要求反复设备或实车回归。
- Git 试验分支隔离不等于 APK 可并存；同包名试验包可能覆盖稳定版，Android `versionCode` 与签名限制不会因手动下载而绕过。必要时另用备用设备或明确可回退的安装隔离方案。
- 临时试验分支按任务创建；完成后先归档完整记录，再经用户确认清理。历史 Release、Issue、提交及 `backup/`、`milestone/` 不擅自删除。
- 默认使用简体中文编写用户可读的记录、说明与更新文案。保护密钥、私有地址与设备唯一识别信息；日志真实时间戳原则上保留。

### 每次构建/交付必须附验收清单（2026-10-26 用户最新确认）

1. **消息和 GitHub 双交付**：今后每轮新实验、功能构建、正式版/实验版 APK 发布、实车测试请求、回滚或重新发布，除了说明改了什么，必须**主动给用户本轮需要验收的具体清单**；不能只写“待实车验收”“CI成功”或让用户自己翻 Issue。
2. **验收清单最少包含**：①本次基线分支、SHA、实际 APK 版本/来源/下载入口（未发布时写明“不可安装/未测试”）；②本轮新增/修复事项；③按操作顺序可直接在手机/车机执行的测试步骤；④每项明确可观察的“通过/失败”判据以及必要的次数、时长（以专项原约定为准，新增数字须标明是新建议）；⑤可能受影响功能的回归项（例如连接、触摸、地图、后台最近任务、软件更新）；⑥故障时提供脱敏日志/视频的方式及回退限制；⑦逐项状态“已实车通过/未测/未通过/不适用”。
3. **区分正式与实验**：如果正式版没有实验功能，分别列明正式版日常回归项与实验版本专项验收项。实验仅 CI 通过但未发布受控签名 APK 时，清单应标“以后安装后再测”，不能暗示用户当前安装包已包含。实验同包覆盖风险、Android versionCode 与签名限制必须显式说明。
4. **验收状态不得越级**：CI 通过只标“构建通过”；用户明确实车确认的项目才标“实车通过”；未知、未覆盖的边界保持“未测”。在专项 Issue 用**追加评论**记录验收结果和失败，正文维护当前标准；#12 同步简明索引。不得把初步正向反馈写成所有车型、所有场景完成。
5. **简短易执行**：面对用户时优先给“本轮必测项”约 3～7 项，附必要回归项；若专项本身已有 10 次切屏、3 轮断连或音频每次≥3分钟等门槛，则原样保留，不得为了方便擅自降低。每次给出能直接回填的通过/失败格式，降低重复沟通成本。
6. **只改文档不触发软件发布**：本条属于流程规范，不更改运行代码、版本、签名与正式 Release。三条长期分支以 Buick 权威版本同步；实验/冻结分支不批量修改。

### 并行实验与同类功能分支管理（2026-10-26 用户明确同意）

**原则：按功能线管理分支、按实验轮次管理提交与独立发布、按实车验收选择性合并。** 多个实验可以并行，不把尚未验证的结果直接写入稳定分支。

1. **同类目标持续沿用**：同一 Issue、同一根因或同一种技术路线的增量优化，继续使用已有 `experiment/<base>-<feature>` 分支（如 `experiment/buick-e5-t68-safe-frame`）。T68-A/B/C 以独立提交、里程碑记录和实验 Release 区分；不得为了换参数每轮重建分支，也不得无限混入不相关问题。
2. **新功能线独立**：UI/GL、导航、音频/iAP2、VPN/网络、设备诊断等不同目的的实验各用独立分支和专项 Issue。一次改动同时跨多个功能线或关键共享文件时，先评估依赖与运行语义冲突，再决定是否拆为基础设施小提交与各专项提交。
3. **重大方案转向新开支线**：若同一目标从外框等比方案改为裁切/非等比渲染，或原技术路线被实车否定后重新设计，可从**最新兼容稳定基线**创建一个新的替代实验分支。旧分支保留提交、失败证据和 Release 记录并标为“已停用/归档待确认”，未经用户明确确认不删除。
4. **每轮实验必留可追溯证据**：至少登记实验代号（如 T68-A）、功能线 Issue、父基线 SHA、改动提交 SHA、状态、构建结果、签名包版本、独立 Release tag、`updaterSchema=2` 元数据、APK/SHA256、测试与回退方式。每次实际发布创建**不可混用的新实验版本和新 tag**，不把新的试验包冒充/覆盖 `*-latest` 正式标签；同一功能分支可连续产生多轮版本。历史失败版本不得因新方案而抹除。
5. **并行安全**：创建/继续实验前核对目标稳定分支当前 HEAD；实验持续期间跟踪共同底层文件、API、虚拟屏和任务生命周期的改动及兼容依赖。合并前重新对比**最新**目标基线，必要时选择性同步基础设施并重新 CI/实车验证；不得为了消除 Git 冲突而未经验证直接整分支合并或覆盖。
6. **合并门禁与职责**：只有达到专项明确设备/实车指标、回归通过且有独立回退方法的功能，才可经 review 选择性 `cherry-pick`/小范围移植至**该任务对应的目标分支**；目标分支须重新构建、发布（如适用）并按其职责验收。若需进入最终正式发行分支 `Buick`，再经独立核验后择优移植；不得因单个实验成功而认定其他分支完成。
7. **APK 不是 Git 分支隔离**：实验同包名可能覆盖手机中的稳定包；版本码、签名及 `baseBranch/sourceBranch` 必须匹配，不能降级覆盖。上车验收前主动给用户独立测试 APK、来源、与稳定版本的安装/回退限制及具体验收表；无可用签名实验包时明确“仅代码/CI通过，尚不能上车测试”。
8. **实验生命周期**：`拟进行 → 代码已提交 → CI通过 → 实验包已发布 → 实车通过/失败/未测 → 已选择性合并/已回滚/归档待确认`。同功能分支完成合并后可保留归档，**后续全新功能**另开分支；清理实验分支及历史 Release 仍须用户明确同意。#12 只放简明索引，逐轮历史放专项 Issue 追加评论。
9. **避免同时碰高风险共享状态**：音频 P0、系统稳定性、GL/触摸/虚拟屏等并行时，各实验的变更范围必须明确，不能将 #11 未验证协议变更顺手带入 UI 实验；遇同一模块同时修改，应先做冲突矩阵和受影响测试，不强行抢先合并。

**当前落实举例：** `experiment/buick-e5-t68-safe-frame` 继续用于 T68 同方向外框/留白迭代，尚未发布测试包、未经实车验证；#11 音频保持其已有独立实验及失败历史；#10 导航待实际编码时才创建独立分支；`Buick-E5` 稳定运行线不接收这两条未验证功能。
