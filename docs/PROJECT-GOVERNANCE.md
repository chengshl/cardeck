# CarDeck 项目协作与发版规范（v3.0）

> 本文件为仓库唯一有效流程规范，取代历史 v1.x / v2.x 全部条款。

## 1. 三条硬底线
1. **保护日用稳定**：未经实车验证的运行代码不合入稳定主线。
2. **保护手机数据**：同包名正式版保持同一签名、`versionCode` 只增不减；不通过卸载清数据降级。
3. **公开隐私边界**：公开 GitHub（提交、Issue、PR、日志摘要）不含 Token/密码、VIN/车机唯一标识、精确家庭/公司地址；原始调试日志仅留私有通道。

## 2. 分支角色
- **`Buick`**：唯一正式主线与规范权威（过渡期 `Buick-E5` 待收拢后归并至此）。
- **`main`**：只同步上游 `shaonialife/cardeck`，不写本地规范或业务提交。
- **`Buick-Test`**：冻结只读，仅保留历史源码与证据，不再开新任务。
- **`exp/<短名>`**：临时功能/修复分支，验证后 Squash Merge 进主线或直接关闭留档。

## 3. 研发与 PR 规则（一题一分支一 PR）
- **一个问题 = 一条分支 = 一个 PR**：在同一分支内连续提交迭代，**禁止叠链式微 PR**（禁止把单一问题拆成互绑父 SHA 的连环 Draft PR）。
- **通用 CI 优先**：全仓只维护通用构建/单测/隐私门禁与手动签名发版 workflow；**禁止为单个 PR 新建一次性专属 workflow**。
- **实验包独立**：实验发版走手动触发，优先使用独立实验包名（`.exp`）与日用包共存，不再例行构建 Recovery APK。
- **合并门槛**：CI 通过 + 实车/手机核心场景确认通过 → Squash Merge 进主线。

## 4. Issue 与进度记录（单一事实源）
- **废止人工大表**：停用 `#12`、`#27` 等手工汇总长表；直接用 **专项 Issue + Labels**（`P0`/`P1`/`P2`、`待实车`）追踪全局状态。
- **正文极简**：专项 Issue 正文只保留当前状态、复现/目标与验收点（≤15 行）；每轮实验结果追加一条简短评论（版本 + 实测现象 + 下一步）。
- **上游同步**：同步 `main` 后仅在 `#23` 记录需要借鉴的条目，不逐 commit 写流水账。
- **默认使用简体中文**，技术名词、日志字段、SHA、版本号保留原文；历史失败记录与备份分支保留不删。

## 5. AI 协作约定（实查实守，禁写八股）
- **动手前必查**：修改或下结论前，必须实时核对目标分支最新 HEAD、关联 Issue/PR 与实际 CI 结果，不凭记忆猜状态，不拿 CI 绿灯当实车通过。
- **按例外汇报（反八股）**：未改动的项（如稳定分支、签名、VPN、音量、上游台账）默认未动，**不要在回复/PR/评论里重复列清单声明**；只有真正改动了、或发现异常/风险时才显式写出。
- **简明交付**：PR、Issue 评论与回复只写三件事——「改了什么 / 验证到哪一步 / 下一步」。
- **CI 通道**：主线默认 GitHub Actions，仅在平台不可用时临时切换备用通道。
