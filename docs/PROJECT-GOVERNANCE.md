# CarDeck 项目统一开发与协作规则

> **统一规范版本：2026-10-27 / v1.9**  
> **唯一权威来源**：`Buick:docs/PROJECT-GOVERNANCE.md`。本文件在 `Buick-E5`、`Buick-Test` 是完全一致的只读同步副本，不允许各分支单独改写规则。与历史 `AGENTS.md`、旧版分支文档、Issue 快照冲突时，按本规则及用户最新明确决定执行。

## 一、仓库与分支边界

| 分支 | 职责 | 规则同步 |
|---|---|---|
| `Buick` | 最终正式发行版，择优吸收集成验证通过的功能；本规则权威分支 | 唯一编辑入口 |
| `Buick-E5` | 当前稳定基准，保障连接、触摸、视频及在线更新可用，持续改善 UI/易用性 | 与 Buick 规则完全同步 |
| `Buick-Test` | **进入冻结与退役收敛期**：只作存量成果迁移来源和既有 CarPlay 音频 P0 专项试验载体，不再承接其他新功能开发或待验证功能的独立实测；迁移完成后申请停用 | 退役前仍与 Buick 规则完全同步 |
| `main` | 上游代码同步线，**不属于本项目规则同步范围** | 不修改 |
| `Buick-main` | 已由 Buick 取代的历史旧分支，保留兼容与追溯 | 不再同步 |
| `experiment/*`、`backup/*`、`milestone/*` | 任务试验、备份与里程碑快照 | 不批量同步；试验时以 Buick 最新规则为准；备份/里程碑不擅自改动 |

### 当前唯一验证主线：Test 向 E5 收敛，逐步退役 Test（v1.6，2026-10-26 用户最新决定）

**本规则优先于历史“两条基线并行开发/并行验收”的计划。当前阶段宁可在 `Buick-E5` 下存在多条尚待验收的独立试验分支，也不再将不同非音频实验分散在 Test 和 E5 两边重复构建、重复验收。** 这是当前战略例外，不改变本规范 L1/L2/L3、实车门禁及 `Buick` 最终正式线职责。

1. **统一收口目标**：`Buick-E5` 是当前唯一的**非音频功能整合基线与手机/实车验证入口**；`Buick` 仍是最终正式发行分支。逐步把 Test 已实现的有用能力、必要基础设施及可复用修复选择性移植到 E5；**不是把 Test 整分支合入 E5**，更不是为了减少分支数而跳过验证。
2. **冻结新增需求和分散验收**：即日起除**CarPlay 音频约20秒断连/重连 P0（#11）**及保障现有 E5 核心能力正常运行的**已发生稳定性阻断故障**外，**不启动新的功能开发或独立验证其他旧有未完成新功能**。非音频新想法、上游新功能候选、原计划中的 UI/GL/导航等功能迭代先登记为暂停，不排进新一轮实施/试车。**唯一许可的非音频验证是 Test→E5 必要迁移验收以及现有 E5 稳定能力的回归/故障恢复**；不得以“迁移”为名夹带额外新功能或扩大试验范围。
3. **Test 限定职责**：`Buick-Test` 及其旧非音频实验分支从现在起只作为**只读来源、追溯或待迁移材料**，不继续开新的 Test 非音频试验、不为相同功能重复发 Test 实验 APK、不让用户再去 Test 验收未完成功能。确属 #11 音频 P0 的现有实验可以继续，必须保持单独试验/风险隔离；如果音频实验在 E5 也需要验证，应另建独立 E5 音频实验，**未经验证不得污染 E5 稳定线**。
4. **一个迁移总账、逐个归宿**：以 [Test→E5 融合主线 #27](https://github.com/chengshl/cardeck/issues/27) 为**唯一迁移台账**，关联原功能 Issue、源 Test 分支/SHA、E5 现有等价实现/差异、风险等级、处理去向、E5 目标试验分支/提交、CI/独立 APK、实车验收、回退和合并结论。将每项归类为：**E5 已有/无需重复；Test 已验证/移植待验收；Test 未验证/迁入 E5 独立试验待验收；音频 P0 独立继续；价值不足/暂停归档**。只清单登记不算代码已迁移。
5. **E5 试验集中管理**：所有确有迁移价值但尚未在 E5 完成验证的非音频成果，从**最新兼容 `Buick-E5` HEAD** 分别派生 `experiment/buick-e5-<feature>`，沿用同功能线已有 E5 试验，**同类实验仅一条活跃目标功能线**。可以有多个 E5 待验分支，但每轮只选择清楚的优先顺序，不要求用户同时测试十个 APK；按 L2/L3 单项验收、记录失败后才继续。旧 Test 实验保留原始证据，不整分支改名或重写历史。
6. **安全迁移与稳定门禁**：E5 现有连接、触摸、视频、虚拟屏、车机蓝牙音源、日志/更新等能力必须守住。L2/L3 只选择性迁移必要提交/逻辑、核对共享文件冲突与差异，先在 E5 实验完成 CI 和用户实际手机/实车验证，之后才能进入 E5 稳定分支，重新构建签名包并回归。**尚未验证、已知失败、测试证据不足的 Test 功能绝不因为“准备淘汰 Test”而直接合入 E5**。现有 E5 P0 如 RECORD 后无视频，应先恢复稳定基线，再让迁移功能上车。
7. **发布渠道与回退**：迁移实验需按 E5 包名/签名、`baseBranch=Buick-E5`、准确`sourceBranch`、`updaterSchema=2` 和独立 prerelease 管理，不复用 Test 正式标签、包名或 APK。测试前说明现有安装版本、是否可覆盖、同包 `versionCode` 单调性以及恢复稳定 E5 的可执行路径；不能把用户手机里的 Test APK 偷换成 E5，也不能通过卸载数据冒充无损回退。
8. **退出 Test 的客观条件**：#27 中每项 Test 独有能力都已有明确去向（E5 已吸收且验收通过 / E5 实验待验继续保留 / 业务价值不足已暂停或归档 / 音频独立继续），E5 可独立承担日常验证和更新，已评估历史 Test APK 用户与更新渠道的迁移、签名/数据/配置限制，必要的回退、诊断和原始 Release 仍可追溯。满足后将 Test 标为**停止新构建和停止新验证的归档线**；是否删除 Test Git 分支、实验分支和历史 Release **必须另获用户明确同意**，本决策不等于立即删除或自动停止规则镜像。最终 `Buick` 仍另行按门禁择优接收成果。
9. **新任务预检必查冻结状态**：每次按第二节复核规范时，先查 #27 和当前 E5 稳定性阻断项，再确认该任务究竟是 **#11 音频 P0／Test→E5 迁移／E5 已有能力稳定性修复／暂停项目**；非前三类不得未经用户更新优先级便恢复并行开发、构建或上车测试。迁移阶段每轮仅维护 #27、原专项 Issue 和 #12 简明状态，不新建冗余迁移项目清单。

### 辅助性诊断与维护优化快速通道（v1.7，2026-10-26 用户最新决定）

**用户明确允许：对不改变 CarPlay 连接、配对、音视频、触摸、虚拟屏或其他主运行能力的辅助优化提高排期优先级，必要时插队处理。** 这是 v1.6 冻结新功能原则的受控例外，仅针对支持已有稳定性诊断、日志管理、脱敏、问题定位和日常运维的必要工具；不意味着恢复已冻结的 UI 美化、导航、新功能、Test 非音频开发或跨线并行验收。

1. **优先级与范围**：用于解除稳定性故障定位阻塞、提高诊断质量的辅助优化可优先于常规迁移/UI待办。优先落到 `Buick-E5` 对应独立功能实验；`Buick-Test` 保持只读迁移来源，非音频不再重复开发/测试。已有 E5 P0 #28 与音频 P0 #11 仍按真实故障严重程度保持优先级，辅助工具可在不影响这两条排障的情况下穿插实施。
2. **优先处理不等于降风险等级**：静态提示 L1 可依风险规则直接处理；系统日志采集、过滤、脱敏、预览、网络分批上传、权限和生命周期一般属 L2，必须独立隔离、CI与手机/上传闭环测试；若涉及主线程阻塞、进程稳定性、Shizuku底层和系统重启风险，则升级 L3。不能仅凭“辅助”两字规避正式门禁。
3. **默认不改变车机运行行为**：诊断开销须限定在用户主动操作和受控后台任务内；原有256行精选、脱敏、敏感凭据过滤、用户主动确认、分批回执和本地导出继续可用；不得悄悄持续抓取或上传系统日志，不得把远程诊断变成控制能力。
4. **交付与验收**：每轮按专项 Issue 记录差异、性能/大小限制、时间窗口、是否截断、实际批次确认/失败和错误恢复。实验 APK 独立签名发布、版本码可安装性和回退限制必须交代；必要手机验证通过后才选择性合入 E5。只改规范文档不触发 APK 构建。
5. **本次执行对象**：#28 的可选详细故障诊断上传（保留256行快速预览，独立增强详细模式）按本条准许优先启动；不能据此把 #28 会话卡死根因认作已修好。

### Xperia 1 V RescueParty 系统重启独立观察与非阻断决定（v1.8，2026-10-26 用户最新决定）

**[设备偶发事件 #31](https://github.com/chengshl/cardeck/issues/31) 的现行归类：疑似 Sony Xperia 1 V / Android 15 固件或系统框架问题，作为独立设备稳定性观察保留，不再与 CarDeck 项目故障强行关联，也不再构成其他功能验证、选择性合并或发布的自动阻断条件。** 本决定以用户明确认可的研发/验收范围为准，优先于此前 Issue 或本规范中“未排除 #31 便禁止合并”的旧表述。

1. **证据与推测分离**：#31 已有 `reboot,rescueparty`、System UID 1000 / SettingsProvider 异常、Sony/Android 系统级恢复记录；存在未连接 CarPlay 时同样发生重启的实证。可合理列为**疑似固件/系统独立偶发**，但未获直接根因证实，**不得把“固件导致”写成事实，也不得宣称已彻底排除 CarDeck/Shizuku 间接影响**。保留全部时间线、bugreport 脱敏摘要及历史记录。
2. **不阻断其他项目**：#31 不再作为 #30 自用详细诊断、#27 / PR #29 Test→E5 功能迁移、以及其他独立功能的**额外**合并/实测阻断；不能继续仅凭“#31 尚未根治”要求暂停上述任务。它们仍须分别完成原有的 L2/L3 代码隔离、CI、签名/版本/回退核对、用户手机或实车验收、回归及选择性合并。
3. **其他故障独立处理**：#28 RECORD 后无视频、#11 AAC 音频断连、#24 蓝牙干扰属于不同 CarDeck 功能问题，**其各自适用的限制仍有效**，不得以 #31 降级为由自动判定这些功能已经修复，或绕过它们自己的合并风险门槛。
4. **观察而非封案**：#31 保留独立开放状态，按设备观察事件而非 CarDeck P0 全局阻断；暂不要求用户为此反复强制复现/重启或暂停全部验证。未来若在清晰受控对照中得到 CarDeck 导致系统重启的直接证据，立即重新评估风险和相应功能的隔离门禁；此前不把时间接近视作确定因果。
5. **记录统一**：#31、#30、#27、#12 和相关 PR 的现行状态须统一注明本决定；**旧评论保存历史、不删除/篡改当时证据**。仅修订项目治理和任务记录，本决定本身不改变 APK 功能或触发发布。

### Test 包名专职系统日志采集例外（v1.9，2026-10-27 用户明确批准）

**新决定：将当前 E5 实验已经在手机验证可采集/本地导出的“重启前系统日志留存”独立出来，形成一套使用 Test Android 包名的专职取证实验 App，长期运行而不承担 CarPlay 连接。E5 继续作为唯一非音频功能融合和车机测试基准。** 本条仅限下面这套受控取证程序，优先于 v1.6/v1.7 的“Test 不再承接任何非音频”一般限制；其它禁令不变。

1. **分支与来源**：单独的 `experiment/buick-test-rescue-collector` 源自 `experiment/buick-e5-detailed-diagnostics` 可用的日志模块，构建 Android 包名为 `io.github.buick.test.cardeck`。**不对冻结中的 `Buick-Test` 主分支做程序功能修改**，不把 E5 或 Test 整条功能分支强行合并，也不恢复 Test 其它非音频实验。此例外只为个人长期取证，不代表 Test 退役战略取消。
2. **双 App 并存**：E5 包名 `io.github.buick.e5.cardeck` 保持独立，专门推进 T22/T26/#28 和后续合规融合；取证包使用 Test 包名，因此与 E5 同机并存。但如果手机已有 Test 原包，此取证 APK **是覆盖升级而非第四套并存**；须核对同签名及高 `versionCode`、维护旧 Test 数据/回滚限制。#11 音频实验的 Test APK 不能与取证包同时作为同包名应用运行，应改换环境或将来经授权改为真正专用包名。
3. **禁止车机自动行为**：取证变体的 Manifest 仅启用专用 `ForensicOnlyActivity`、用户主动启停的 `RescueTraceService` 与所需 Shizuku provider；不暴露/自动启动 `CarPlayService`、主连接界面、蓝牙/HFP/A2DP、Wi-Fi、虚拟显示、Gateway 网络服务、通知监听或声音录制能力。源代码里若保留未引用连接实现，不代表可在该包运行；打包校验必须检查 Manifest 权限与组件边界。
4. **取证生命周期与隐私**：Shizuku 必须按 Test Android 包名单独授权；用户手动启动 `specialUse` 常驻通知取证，无应用层4小时时限，脱敏后只保存本机 4×512 KiB 滚动文件，不暗中网络上传；手动停止/导出到下载目录。系统杀进程、Shizuku断开或整机重启仍会停止采集，已同步落盘的文件跨系统重启保留，但**默认不自启动**。清除Test数据/卸载前先导出旧记录。
5. **研发与发布边界**：本辅助工具改动风险 **L3**，单独 CI/签名/预发布 tag，不覆盖 Buick 正式 `latest` 或 E5 包名；须验收“可与 E5 并存、Shizuku授权、通知、采集/脱敏/停止/导出、E5覆盖升级期间不被触发断开、原有 Test 音频版本覆盖风险”，再标记手机验收通过。版本元数据必须真实记载源码实验分支、构建SHA与 Test applicationId，不因直接构建成功就当作长期稳定。
6. **维护归属**：设备 RescueParty 证据继续汇总 #31，取证代码与交付在 #30 及 #12 登记，Test→E5迁移关系只在 #27 留简明记录。E5 后续正常功能融合按原 v1.8 L2/L3 验收，不必等这套自用采集工具查明 #31 的固件根因。

## 二、规则更新：一个权威版本、立即同步

1. 用户确认**开发规范、分支职责、命名、发布原则、记录格式、验收门槛、流程约定**等非运行功能决定后，在当次工作中立即更新 `Buick:docs/PROJECT-GOVERNANCE.md`，并同步同一字节内容到 `Buick-E5` 与 `Buick-Test`；同时按需在 GitHub Issue 留决策依据。不要只写聊天记录或当前工作分支。
2. `Buick` 的 `.github/workflows/sync-project-governance.yml` 对本文件的推送提供自动镜像，以尽量避免各分支规则漂移。同步失败时记录原因并及时补齐，**不能宣称未成功的同步已完成**。
3. 子分支 `AGENTS.md` 只保留与本分支代码有关的技术说明和指向本文件的入口；不能另建与统一规则冲突的独立治理制度。历史文档保留供追溯，但不改变本规范优先级。
4. **纯规则/文档提交不是软件更新**：不能因为修订 `docs/**`、`AGENTS.md` 等文档就自动构建或发布正式 APK。构建工作流配置路径过滤；文档同步禁止更改运行源码、包名、签名和版本号。
5. 当一次提交同时含运行功能变更和文档时，仍按功能变更完整执行对应 CI / APK 发布与验收流程；不得用 `[skip ci]` 绕过功能变更检查。手动触发正式构建须有明确需求。

### 每次任务启动前必须复核规范（v1.3，2026-10-26 用户明确要求）

**强制起点，不依赖聊天记忆：** 每当在新聊天中处理 CarDeck，或在已有聊天中开始一项新的、继续一项中断的开发/诊断/发布/记录任务时，**在提出实施方案、修改任何仓库内容、运行构建或给出基于旧进度的处理决定之前**，先实时读取 `Buick:docs/PROJECT-GOVERNANCE.md` 当前版本全文，并依次核实：

1. **规则与同步状态**：记录权威规范版本/提交或文件哈希，核对 `Buick-E5` 与 `Buick-Test` 的规则内容是否一致，以及最近镜像工作流是否成功；不得沿用上轮聊天记住的版本或把同步任务已启动当成同步成功。
2. **任务与代码现状**：从 #12 当前有效入口定位所属专项 Issue，阅读相关的最新结论与逐轮历史评论；核对目标分支当前 HEAD、最近提交、CI/Release、测试及回滚限制。#12 的历史快照、旧 `Buick-main`、过期版本号与旧渠道规则**不得高于本规范和用户最新明确决定**。
3. **先确认风险与操作边界**：按 L1/L2/L3 及当前功能线选对稳定/试验分支，明确本轮允许修改、必须隔离、待实车验证的范围；需要构建或交付时准备对应验收清单。新聊天继续旧实验应核对最新基线，不能盲目重开同功能分支。
4. **启动结论留痕**：处理实质任务时，在回复中简要说明使用的规范版本、目标分支、风险等级及发现的冲突；属于开发/实验的项目继续在专项 Issue 追加真实状态。预检不要求在每一次工具调用前重复，也不能变成阻碍简单问答的冗长仪式。
5. **规则变化与失联**：任务进行期间发现规范或用户决定已更新，应以最新权威文本重新确认影响后再合并/发布；若暂时无法读取权威规范或验证同步，明确告知“未核实”，**不得宣称符合规范，也不得贸然执行高风险变更、合并或发布**，待可核验后继续。

此项是**工作开始前的检查义务**，不能只靠 #12 提醒或助手的历史聊天记忆替代；仅更新文档及镜像流程，**不改变 APK 功能、签名、版本、构建或正式发布渠道**。

## 三、通用开发风险分级（适用于 CarDeck 所有活跃目标分支）

**风险分级是整个 CarDeck 项目的通用规则，不专属于 `Buick-E5`，也不决定默认修改哪条分支。** 每次先根据任务功能、分支职责和最新基线确定实际目标分支，再依风险等级决定实施、测试和合并门槛。

| 风险 | 典型改动 | 最小验证流程 |
|---|---|---|
| L1 低风险 | 纯静态文字、颜色、图标、间距，不改行为 | 可在**本次对应目标分支**直接修改；进行代码审查、必要的 CI 与适用的视觉/功能验证 |
| L2 中风险 | 更新页面与弹窗逻辑、APK 下载/安装、版本来源、权限、设置存储、生命周期 | 从**本次对应目标分支**建立独立短期 `experiment/<target>-<task>`；通过相关手机/功能验证后，选择性合入该目标分支 |
| L3 高风险 | CarPlay/iAP2/蓝牙/Wi-Fi、音视频流、Shizuku/虚拟屏、系统崩溃/重启 | 从兼容基线建立独立试验；预备可执行回退方案，明确设备/实车验收指标并做多轮实际测试；通过后才考虑选择性合入对应目标分支 |

**`<target>` 是目标分支/功能线的规范化标识，不固定为 `buick-e5`。** 例如针对 `Buick-Test` 的实验应从最新 Test 兼容基线派生，而不能仅因风险分级示例就强行转向 E5；针对其他分支同理。分支的正式发行/稳定/集成职责仍以本文件第一节为准。

按**潜在破坏的能力**分类，不按代码量大小判断；多个等级混合时从高。未验证的高风险代码不得直接进入任何承担稳定/正式使用职责的分支。

## 四、验证、交付与记录

- 每轮在相关专项 Issue 记录目标、风险级别、基准/试验分支、提交 SHA、CI、APK 版本与更新来源、测试条件、脱敏日志或截图、成功/失败/未测、结论、下一步、回滚策略。#12 为总清单索引；#17 为更新架构/试验版本相关专项。
- 明确区分：**仅方案 → 已提交 → CI通过 → APK已发布 → 手机端/实车验收通过 → 完成**。CI 通过不代表手机 UI 或车机稳定性通过。
- 试验验证通过后只合并所需提交/文件，不用整分支覆盖；**每条实际接收改动的目标分支**均须重新核验、构建与按职责独立发布/验收。高风险问题要求反复设备或实车回归。
- Git 试验分支隔离不等于 APK 可并存；同包名试验包可能覆盖稳定版，Android `versionCode` 与签名限制不会因手动下载而绕过。必要时另用备用设备或明确可回退的安装隔离方案。
- 临时试验分支按任务创建；完成后先归档完整记录，再经用户确认清理。历史 Release、Issue、提交及 `backup/`、`milestone/` 不擅自删除。
- 默认使用简体中文编写用户可读的记录、说明与更新文案。保护密钥、私有地址与设备唯一识别信息；日志真实时间戳原则上保留。

### 每次构建/交付必须附验收清单（2026-10-26 用户最新确认）

1. **消息和 GitHub 双交付**：今后每轮新实验、功能构建、正式版/实验版 APK 发布、实车测试请求、回滚或重新发布，除了说明改了什么，必须**主动给用户本轮需要验收的具体清单**；不能只写“待实车验收”“CI成功”或让用户自己翻 Issue。
2. **验收清单最少包含**：①本次基线分支、SHA、实际 APK 版本/来源/下载入口（未发布时写明“不可安装/未测试”）；②本轮新增/修复事项；③按操作顺序可直接在手机/车机执行的测试步骤；④每项明确可观察的“通过/失败”判据以及必要的次数、时长（以专项原约定为准，新增数字须标明是新建议）；⑤可能受影响功能的回归项（例如连接、触摸、地图、后台最近任务、软件更新）；⑥故障时提供脱敏日志/视频的方式及回退限制；⑦逐项状态“已实车通过/未测/未通过/不适用”。
3. **区分正式与实验**：如果正式版没有实验功能，分别列明正式版日常回归项与实验版本专项验收项。实验仅 CI 通过但未发布受控签名 APK 时，清单应标“以后安装后再测”，不能暗示用户当前安装包已包含。实验同包覆盖风险、Android versionCode 与签名限制必须显式说明。
4. **验收状态不得越级**：CI 通过只标“构建通过”；用户明确实车确认的项目才标“实车通过”；未知、未覆盖的边界保持“未测”。在专项 Issue 用**追加评论**记录验收结果和失败，正文维护当前标准；#12 同步简明索引。不得把初步正向反馈写成所有车型、所有场景完成。
5. **简短易执行**：面对用户时优先给“本轮必测项”约 3～7 项，附必要回归项；若专项本身已有 10 次切屏、3 轮断连或音频每次≥3分钟等门槛，则原样保留，不得为了方便擅自降低。每次给出能直接回填的通过/失败格式，降低重复沟通成本。
6. **只改文档不触发软件发布**：本条属于流程规范，不更改运行代码、版本、签名与正式 Release。三条长期分支以 Buick 权威版本同步；实验/冻结分支不批量修改。

### 并行实验与同类功能分支管理（2026-10-26 用户明确同意）

**原则：按功能线管理分支、按实验轮次管理提交与独立发布、按实车验收选择性合并。** 多个实验可以并行，不把尚未验证的结果直接写入稳定分支。

1. **同类目标持续沿用**：同一 Issue、同一根因或同一种技术路线的增量优化，继续使用已有 `experiment/<base>-<feature>` 分支（如 `experiment/buick-e5-t68-safe-frame`）。T68-A/B/C 以独立提交、里程碑记录和实验 Release 区分；不得为了换参数每轮重建分支，也不得无限混入不相关问题。
2. **新功能线独立**：UI/GL、导航、音频/iAP2、VPN/网络、设备诊断等不同目的的实验各用独立分支和专项 Issue。一次改动同时跨多个功能线或关键共享文件时，先评估依赖与运行语义冲突，再决定是否拆为基础设施小提交与各专项提交。
3. **重大方案转向新开支线**：若同一目标从外框等比方案改为裁切/非等比渲染，或原技术路线被实车否定后重新设计，可从**最新兼容稳定基线**创建一个新的替代实验分支。旧分支保留提交、失败证据和 Release 记录并标为“已停用/归档待确认”，未经用户明确确认不删除。
4. **每轮实验必留可追溯证据**：至少登记实验代号（如 T68-A）、功能线 Issue、父基线 SHA、改动提交 SHA、状态、构建结果、签名包版本、独立 Release tag、`updaterSchema=2` 元数据、APK/SHA256、测试与回退方式。每次实际发布创建**不可混用的新实验版本和新 tag**，不把新的试验包冒充/覆盖 `*-latest` 正式标签；同一功能分支可连续产生多轮版本。历史失败版本不得因新方案而抹除。
5. **并行安全**：创建/继续实验前核对目标稳定分支当前 HEAD；实验持续期间跟踪共同底层文件、API、虚拟屏和任务生命周期的改动及兼容依赖。合并前重新对比**最新**目标基线，必要时选择性同步基础设施并重新 CI/实车验证；不得为了消除 Git 冲突而未经验证直接整分支合并或覆盖。
6. **合并门禁与职责**：只有达到专项明确设备/实车指标、回归通过且有独立回退方法的功能，才可经 review 选择性 `cherry-pick`/小范围移植至**该任务对应的目标分支**；目标分支须重新构建、发布（如适用）并按其职责验收。若需进入最终正式发行分支 `Buick`，再经独立核验后择优移植；不得因单个实验成功而认定其他分支完成。
7. **APK 不是 Git 分支隔离**：实验同包名可能覆盖手机中的稳定包；版本码、签名及 `baseBranch/sourceBranch` 必须匹配，不能降级覆盖。上车验收前主动给用户独立测试 APK、来源、与稳定版本的安装/回退限制及具体验收表；无可用签名实验包时明确“仅代码/CI通过，尚不能上车测试”。
8. **实验生命周期**：`拟进行 → 代码已提交 → CI通过 → 实验包已发布 → 实车通过/失败/未测 → 已选择性合并/已回滚/归档待确认`。同功能分支完成合并后可保留归档，**后续全新功能**另开分支；清理实验分支及历史 Release 仍须用户明确同意。#12 只放简明索引，逐轮历史放专项 Issue 追加评论。
9. **避免同时碰高风险共享状态**：音频 P0、系统稳定性、GL/触摸/虚拟屏等并行时，各实验的变更范围必须明确，不能将 #11 未验证协议变更顺手带入 UI 实验；遇同一模块同时修改，应先做冲突矩阵和受影响测试，不强行抢先合并。

**当前落实举例：** `experiment/buick-e5-t68-safe-frame` 继续用于 T68 同方向外框/留白迭代，尚未发布测试包、未经实车验证；#11 音频保持其已有独立实验及失败历史；#10 导航待实际编码时才创建独立分支；`Buick-E5` 稳定运行线不接收这两条未验证功能。

## 五、上游优化与已融合/借鉴功能台账（v1.5，2026-10-26 用户确认）

1. **唯一上游候选源**：直接分析本仓库**已同步的 `main`** 的提交、文件及测试差异；不要求另抓外部上游来代替 `main`。但 `main` 的“已同步状态”不代表它实时等于外部最新上游，必要时另核对同步时点。**严禁向 `main` 写我们的项目规范、融合记录或试验业务代码。**
2. **唯一持续台账**：[上游融合/借鉴台账 #23](https://github.com/chengshl/cardeck/issues/23) 与权威快照 [`Buick/docs/UPSTREAM-ADOPTION-LEDGER.md`](https://github.com/chengshl/cardeck/blob/Buick/docs/UPSTREAM-ADOPTION-LEDGER.md)。`Buick` 管记录；E5/Test 只使用同一入口，不各自维护会分叉的“上游清单”。#12 仅维护简明入口/主要结论。
3. **每次评估记录来源和实证**：上游 `main` 的源 SHA、变更目标、核心模块与行为、对 E5/Test/Buick 分别是否适用、风险等级、代码/协议冲突、采纳决策、相关 Issue、试验分支、目标提交、CI/Release、实际设备验收与回退措施。和当前 E5/Test 自研功能的重叠也要列明。
4. **待融合与已经融合同等重要**：永久保留状态历史，明确区分**候选待评估、决定不采用、上游基础代码已同源、已借鉴改写、试验中、目标分支代码已移植、目标分支已融合并构建、设备/实车验收成功、撤回或弃用**。已借鉴的非原样实现必须写目标提交及设计差异；相同文件 blob SHA 仅能证明该文件当前内容相同，不能凭此断言某个上游提交已完整 cherry-pick。未测不得标实车通过。
5. **同步动作**：每次 `main` 代码同步后、每次处理上游技术问题或从上游引入/借鉴功能时，立即更新 #23 台账（重要结果同步 #12）；不因每次上游提交自动产生测试 APK。**文档/规则提交不得触发软件更新**；真正功能移植按第三、四节的风险分级、隔离试验、CI 和手机/实车验收逐项执行。
6. **多分支采纳状态分开写**：即使 Test 已接入，也不能默认 E5、Buick 已接入；自研 E5 → Test 的移植同样记录借鉴与验收链，来源标识明确，不能冒充 `main` 上游贡献。
